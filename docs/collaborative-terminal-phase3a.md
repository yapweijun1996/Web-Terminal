# Phase 3A input gateway: work in progress

**P0 OPEN. Do not expose or deploy this implementation.** The collaboration launcher remains fail-closed. The broker is an isolated building block and is not yet the authority for existing browser, MCP or upload routes.

## Current mutation inventory and trust boundary

* `runtime/serve.sh` launches writable ttyd on a Unix socket. `runtime/attach.sh` attaches a full tmux client to a grouped session. Browser WebSocket input reaches the attached tmux client, including text, paste, control keys and tmux key bindings; terminal resize can affect tmux geometry. The socket is private to the OS user, but a network origin proxy can make ttyd reachable. `--check-origin` is not authentication. The checked-in client (`client/src/components/terminal/xterm/index.ts`) sends a first JSON handshake with `AuthToken`, columns and rows, then binary frames prefixed `0` for input, `1` for resize, `2` for pause and `3` for resume, using WebSocket subprotocol `tty`. This is source evidence, not a live verification of the installed ttyd server; no WebSocket filter is implemented here.
* `mcp/server.js` exposes type/key/select/new-window through `mcp/terminal.js`; type uses set-buffer/paste-buffer, key uses send-keys, and selection and window creation also mutate tmux state. The legacy HTTP Unix socket rejects Origin but does not identify the caller; stdio has its own process boundary.
* `runtime/upload-server.js` calls `runtime/upload-target.js`: insertion uses paste-buffer and return-to-live uses copy-mode send-keys. Upload view UUIDs and tickets identify a target/receipt, not an authenticated principal. File creation is separate from terminal insertion.
* Existing origin/proxy, legacy launchers and any direct paths must not be connected to a collaboration workspace until every mutation is mediated. A ttyd read-only flag alone must be verified against resize and other behavior before use.

Network clients are untrusted. A trusted origin must authenticate each connection before assigning a principal and permissions; neither an Origin header, a client label, a view UUID nor a supplied tmux ID is proof. The broker's `connect` is a privileged in-process API, not an authentication mechanism. Any eventual Unix socket must live in an owner-only directory, be mode 0600 and be reachable only by the trusted adapter, with no route that accepts client-selected identity or permissions. Same-UID host processes can control tmux directly and are explicitly inside the trusted host boundary; this design does not protect against them. Do not place the raw ttyd socket behind an untrusted route.

## Current file contracts

`runtime/gateway/broker.js` exports `InputBroker`. Trusted code constructs it with an asynchronous target verifier and executor. It supplies an authenticated principal and permissions to `connect` and retains the returned opaque connection object; untrusted data must never invoke `connect`. `claim`, `renew`, `release`, `mutate`, and `disconnect` serialize through one queue. A lease is bound to one connection, complete target identity, random token, and restart-unique generation. The key is tmux server PID plus pane ID, preventing separate leases via different session views. Takeover requires an explicit flag and trusted takeover permission. Disconnect invalidates a connection immediately. Expiry is checked against monotonic time. The executor must repeat target checks atomically in tmux; the broker alone cannot prevent same-UID tmux bypass or an already dispatched command after disconnect. An in-flight command completes before takeover is granted; uncertain input must not be retried automatically.

`mcp/input-gateway.js` connects the broker to the existing target-validating tmux controller for text and key operations, but is not used by `mcp/server.js` or any exposed route. Its in-process API does not authenticate callers. `mcp/test/input-gateway.test.js` is a disposable real-tmux fixture, which could not pass in the current sandbox because tmux socket creation was denied.

`tests/input-broker.test.js` tests policy and concurrency using a controlled executor, not a transport security acceptance test. Existing legacy contracts are unchanged. No principal provisioning, socket transport, WebSocket upgrade authorization, ttyd adapter, MCP/upload adapter, or browser UI is implemented.

## Acceptance still required

Authenticate before WebSocket upgrade; prove direct ttyd/MCP/upload paths cannot bypass the policy, including input, controls, Enter, paste, resize and upload insertion. Test two independently authenticated principals against a disposable real tmux/ttyd stack and verify stale connections, takeover, reconnect, target replacement and upload. Define a trusted identity propagation contract first; do not infer identity from untrusted request fields. Keep production independent and the collaboration launcher closed until the full boundary is proven.
