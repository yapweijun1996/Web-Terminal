# Restart retention: candidate security boundary

Status: **PARTIAL, not production-ready**. This build cannot authenticate an independent writer and never automatically deletes a recovered record. `restartRetentionPolicy({optIn:true})` reports `TRUSTED_VERIFIER_UNAVAILABLE`; opt-in is a request, not a trust grant. `JobManager.previewMigration({limit})` is a bounded, read-only inventory with refusal reasons; it does not initialize the manager, acquire a lock, modify files, attest, migrate, or enable deletion. For example, from the repository root use `node --input-type=module -e 'import {previewLegacyMigration} from "./mcp/restart-retention.js"; console.log(JSON.stringify(previewLegacyMigration(process.argv[1]), null, 2))' /absolute/registry/path`. Inventory is not a consistent snapshot under concurrent writers, must be reviewed offline, and reports truncation. It never treats any entry as migration eligible. No extra MCP tool is exposed.

## Current threat model

The executable, supervisor and MCP server run under the same OS UID. An arbitrary job can read and replace registry files, manipulate lock state and same-UID key material, forge JSON, status, migration flags, signatures, counters, owner names and stdout, and deny service. MCP OAuth authenticates a remote client to MCP; it does not change the spawned process's OS identity or authenticate local file ownership. File modes, lock tokens, inode checks and no-follow checks protect against mistakes and some substitutions, not a malicious process with equal OS authority. A same-UID HMAC key offers no authenticity. The supervisor IPC lifecycle is meaningful only inside the live controller, not independently verifiable after restart; the supervisor itself shares the untrusted UID. Crashes can leave unknown outcomes and temporary files. Recovered nonterminal jobs become interrupted with unknown outcome; all recovered records remain ineligible, including previously completed ones. Corruption, unexpected files, symlinks, permissions drift, and quota exhaustion fail closed and can block admission. No cleanup of ambiguous data is attempted.

The live controller retains an in-memory digest of the final record it successfully saved after a locally observed completion. It permits normal local retention only while that digest matches, the job is inactive and the outcome is known. This is not a signature or cross-restart proof. A same-UID adversary can still race path checks against unlink, modify a file after a check, interfere with the process or its memory where OS policy permits, or delete records directly. Node's path-based lstat/unlink sequence is not an atomic conditional unlink; these checks do not establish security against a concurrent same-UID adversary. Do not present local retention as an isolated security boundary.

## Candidate independent verification service contract

A future, separately reviewed implementation must run both the authoritative lifecycle supervisor and Registry Writer/verification service under a dedicated OS principal that the command cannot impersonate, signal, debug, configure, or write to. The writer's private data, executable, configuration, persistent anti-replay state and any signing keys must be owned and protected by that principal or stronger authority; the caller must not read signing keys. Merely moving the writer while leaving the supervisor under the command UID is insufficient. The writer must create and control the job lifecycle and observe actual process exit/termination directly; an event from the caller, an exit status, stdout, PID, a caller-selected owner, or a boolean `attested` is never completion evidence. If the platform cannot provide this evidence, the service must return unknown and deny deletion.

The intended bounded event interface accepts a versioned request ID and job ID, with strict size/time limits and a closed set of request types. The caller may request close/outcome lookup, but the service derives the outcome from its own supervisor and sends back a bounded response only. The channel must be OS-owned and authenticated in both directions: the service checks kernel-provided peer credentials against reviewed OS identities, and the client authenticates the service endpoint/peer without trusting request fields, writable paths or environment variables. A portable Node peer-credential API and such a service are not implemented here. No caller-supplied adapter, peer UID, proof object, or opt-in flag can activate verification in this build.

A future service must bind each eligible record to a unique job ID, lifecycle instance, canonical immutable record content, observed terminal outcome and authenticated supervisor identity. Its durable, crash-consistent monotonic per-record version and unique nonce must reject replay, rollback, duplicate or reordered events across restart; a signed-proof design additionally requires protected signing keys, independently protected verification keys and reviewed key rotation/revocation. A verification-service design must protect its authoritative history and authenticate every response. Both require atomic record publication, durability and deletion coordinated by the trusted writer itself over its protected directory; a same-UID caller doing path-based unlink after verification is not sufficient. Treat malformed, stale, missing, unrecognized or unverifiable proofs as ineligible. Enforce explicit bounds and deny on exhaustion or uncertainty. Neither mode exists yet.

## Legacy and operational policy

Legacy records, including forged migration markers and completed records, are quarantined in place and consume quota; the preview reports reasons only. A future migration must not manufacture completion provenance from those records. Any eligibility decision needs independent trusted lifecycle evidence, separately authorized review and a crash-safe idempotent plan; where such evidence does not exist, preserve the record or handle it through a separate explicitly authorized manual procedure. Preserve corrupt, active, orphaned, interrupted and unknown-outcome records. Unexpected temp records or permission drift should block automatic operations and require investigation; do not follow symlinks or accept path traversal. Directory scans and record reads are bounded in the preview; concurrent changes remain ambiguous. Repeated previews have no intentional effects.

## Reviewer-gated platform provisioning plan (not executed)

1. Security and platform reviewers approve a design covering service/supervisor ownership, OS peer credential primitives, protected endpoint and ancestor directories, non-impersonation, lifecycle evidence, durable monotonic anti-replay state, atomic trusted deletion, threat model and quota recovery. Review the exact target OS and Node/native interface; do not assume cross-platform behavior.
2. In an isolated staging host, an authorized operator provisions separate least-privileged principals and private storage, deploys the independently owned service and supervisor, and configures authenticated communication and a disabled-by-default policy. This work requires explicit authorization and is not included here. Protect the service from the command UID including debugging, inherited descriptors, configuration, launch mechanisms and writable ancestors.
3. Independent reviewers exercise real peer identity impersonation, same-UID attacks, symlink/rename races, concurrent updates, key compromise/rotation if applicable, replay and rollback, crash at every durable transition, quota exhaustion, orphan process and unknown outcome. Verify actual principals and permissions from the OS, not reported configuration. Confirm logs contain no secrets and preserve rollback evidence.
4. Release only after independent security approval, native target-platform tests, operational monitoring, recovery and retention policies, and explicit authorization. Gate on verified independent writer, trusted supervisor, authenticated peers, isolated storage and atomic deletion; missing evidence means disabled. OAuth and a successful signature test alone do not pass these gates.
5. Roll back by disabling the opt-in and stopping trusted deletion using the reviewed deployment procedure; preserve registry, audit and anti-replay state. Do not reset counters, reclassify records or delete artifacts as part of rollback. Reconcile in-flight jobs as unknown until independently established.

## Isolated executable candidate (not a service deployment)

`registry-writer-protocol.js` is a portable, bounded parser and a pure in-memory transition simulation. Version 1 accepts only a UTF-8 JSON `outcome` request with exactly `version`, `type`, `request_id`, `job_id`, and a 32-byte hexadecimal nonce; both identifiers must be UUIDv4. Frames are limited to 4096 bytes. No request supplies status, stdout, supervisor identity, or deletion instruction. A real transport must also impose a finite frame/read and response deadline, enforce framing and connection quotas before buffering, and bind requests to the authenticated channel. The simulation checks instance, sequence and nonce in memory only; it is neither durable nor trusted evidence, and is not connected to production.

`registry-writer-transport.js` provides an unimplemented macOS verifier which always raises `TRUSTED_VERIFIER_UNAVAILABLE`; `registry-writer-service.js` is a non-listening candidate facade that always refuses valid requests. No injection, environment flag or client credential can enable it. This is a skeleton, not an independent supervisor, writer, durable anti-replay journal, proof store, ACL, atomic publication or deletion implementation. In particular, the simulation cannot detect rollback across restarts, validate proof integrity or recover after a crash. There is no claim of cross-restart automatic eviction, and no changes to legacy preview or the existing 11-tool surface.

### Required platform design and release evidence

The proposed design needs a dedicated service OS principal distinct from the command principal, with both the lifecycle supervisor and registry writer under that authority. A reviewed native Unix-domain-socket helper could retrieve peer credentials from the actual accepted socket using the target macOS kernel API; validate the exact OS version, peer lifetime, effective credentials, PID reuse and endpoint identity independently. If those properties cannot be established, evaluate an XPC service with independently validated audit-token and code-signing policy. A claimed UID, client-supplied proof, same-UID secret or injected callback is never evidence. Mutual authentication and a protected endpoint are required; no transport in this repository implements them.

An authorized operator would stage a disabled-by-default launchd job using root-owned configuration and executable ancestors, a least-privileged service account, and protected socket, journal, proof and registry directories. Independently inspect each ancestor and ACL, ownership, inherited descriptors, debug/signal rights, code identity and actual process credentials; do not trust environment configuration. Use directory-relative no-follow operations with stable directory descriptors in a reviewed native component, strict ownership and ACL checks, same-directory exclusive temporary files, file fsync, atomic rename and directory fsync. Fail closed on unsupported operations, drift, quota, symlinks, uncertainty, or sync failure. An authenticated journal needs protected durable monotonic state, sequence, instance and nonces, a crash-recovery protocol and an independently protected rollback anchor; a hash chain alone cannot detect whole-store rollback. Keys, if used, must remain inaccessible to command processes, with exposure, rotation and revocation procedures. A proof must bind the exact record and observed supervisor lifecycle; the writer alone may delete after checking protected evidence and ACLs. No PID alone proves process identity or completion. Split brain and in-flight work become unknown; process group escape must be independently contained or remain unknown rather than treated as terminated.

Manual legacy migration begins with the existing bounded read-only preview, records a reviewed snapshot and explicitly identifies unknown or unprovable provenance. A separately authorized operator must review a dry-run plan, independently establish any evidence, obtain approval for each irreversible action, and use a crash-safe staged procedure; fabricated completion proofs and automatic classification from old JSON are prohibited. Stage a rollback by disabling deletion first and preserving journal, proof store and records, then stop the service without resetting counters. Reconcile in-flight jobs as unknown. No provisioning, migration or rollback is performed by this candidate.

The release gate requires independent signed evidence from all 13 roles: (1) service owner, (2) macOS platform engineer, (3) OS security engineer, (4) native IPC reviewer, (5) process lifecycle engineer, (6) storage/durability engineer, (7) cryptography/key custodian, (8) adversarial tester, (9) QA lead, (10) operations/SRE, (11) incident responder, (12) privacy/audit reviewer, and (13) release approver. Each must review their scope and blocking findings; absence, unresolved P0/P1, or failed target-host tests keeps activation disabled. Evidence must cover same-UID and peer impersonation, forged credentials, wrong principal, PID reuse, split brain, in-flight unknown, escaped process groups, replay/rollback, key exposure, malformed frames and deadlines, tampered proofs, read-only quarantine, symlink/ancestor drift, storage quota and injected failures at every write/fsync/rename boundary. This is a future gate, not a claim that reviews or target-host tests occurred.
